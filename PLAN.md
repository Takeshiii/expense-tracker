# Expense Tracker — план пет-проекта

Трекер личных расходов. Цель — не продукт, а разобраться в бэкенде на стеке, близком к продовому:
.NET, Postgres, Kafka, кэши, объектное хранилище, аналитика, наблюдаемость. Каждая технология
появляется только под фичу, которой без неё плохо.

## Фичи и что на них учится

| Фича | Технология | Что поймёшь |
|---|---|---|
| Добавить трату: сумма, категория, дата, заметка | Postgres, EF Core, миграции, GraphQL | Схема, миграции, API. Деньги — `decimal` |
| Разбить чек на категории (еда + бытовое) | Транзакция в БД | Все части сохраняются вместе или ничего |
| Одну трату правят из двух вкладок | Оптимистичная блокировка (`RowVersion`) | Как поймать конфликт одновременной правки |
| Фото чека | MinIO (S3), imgproxy | Где хранить файлы, превью на лету |
| Траты в другой валюте | Внешний API курсов, Dragonfly | Кэш со временем жизни; что делать, когда API лежит |
| Импорт банковской выписки (CSV) | Kafka, фоновая обработка, Redis | Асинхронная задача; повторный импорт не задваивает траты |
| Бюджет на категорию, «превысил лимит» | Отдельный сервис, читающий Kafka | Копия данных отстаёт; дубль события может посчитать трату дважды |
| Подписки (Netflix, спортзал) | Планировщик фоновых задач | Ровно одно проведение по расписанию, даже после рестарта |
| Отчёт «куда ушли деньги за год» | Postgres, затем Debezium → Kafka → ClickHouse | Где Postgres перестаёт тянуть и зачем колоночная база |
| Мониторинг приложения | Prometheus, Grafana, Loki, Sentry-совместимый трекер | Метрики, логи и ошибки своего сервиса |

## Архитектура

Четыре сервиса, у каждого своя база. Общаются только через Kafka или HTTP.

| Сервис | Отвечает за | Хранилища |
|---|---|---|
| `expenses` | Траты, категории, чеки, подписки. Единственный источник правды | Postgres, MinIO, Dragonfly |
| `importer` | Разбор банковских выписок в фоне | MinIO, Redis |
| `budgets` | Лимиты и уведомления. Держит свою копию сумм по категориям | Postgres (своя база) |
| `analytics` | Отчёты по большим объёмам | ClickHouse, наполняется через Debezium |

Правила границ:
- Сервис ссылается только на `contracts`, на проекты других сервисов — никогда.
- В чужую базу не ходит ни один сервис. Локально все базы могут жить в одном контейнере Postgres,
  но это разные базы с разными пользователями.
- `contracts` — только классы сообщений Kafka, без логики.
- `importer` не пишет траты сам: он публикует событие, `expenses` его принимает.

## Раскладка репозитория

Внутри каждого сервиса одно и то же деление:
- `Model` — домен: сущности и правила, без базы, Kafka и HTTP. Тестируется без инфраструктуры.
- `Infra` — всё, что ходит наружу: база, Kafka, S3, кэш, внешние API.
- `Api` — точка входа для запросов: GraphQL или REST.
- `Worker` — фоновые задачи и консьюмеры Kafka. Отдельный процесс, масштабируется отдельно от `Api`.
- `Migrator` — миграции схемы. Запускается до старта сервиса и завершается.

## Стек

- **Бэкенд:** .NET 10, HotChocolate (GraphQL), EF Core + Npgsql, FluentMigrator, Confluent.Kafka,
  FusionCache, Testcontainers.
- **Хранилища:** Postgres, Dragonfly (кэш, можно потерять), Redis (ключи идемпотентности — терять
  нельзя), MinIO, ClickHouse.
- **Транспорт:** Kafka 4 в режиме KRaft (без ZooKeeper), Debezium через Kafka Connect.
- **Картинки:** imgproxy.
- **Наблюдаемость:** prometheus-net, Prometheus или VictoriaMetrics, Grafana, Loki, Vector для логов,
  GlitchTip или облачный Sentry для ошибок. Self-hosted Sentry — около двух десятков контейнеров,
  для пета это перебор.
- **Курсы валют:** бесплатный XML ЦБ РФ (`https://www.cbr.ru/scripts/XML_daily.asp`).
- **CI:** GitHub Actions — сборка и тесты на каждый пуш.

Всё поднимается одной командой: `docker compose up`.

## Этапы

Каждый этап заканчивается рабочей фичей. «Сломай нарочно» — обязательная часть: именно так
запоминается, зачем нужна технология.

### Этап 0. Скелет
- [ ] Репозиторий, solution, `Directory.Packages.props`, `.editorconfig`
- [ ] docker-compose с Postgres
- [ ] `expenses`: пустой GraphQL API с health check
- [ ] GitHub Actions: сборка и тесты

### Этап 1. Траты
- [ ] Категории и траты: миграции, EF Core, GraphQL-запросы и мутации
- [ ] Разбиение чека на части в одной транзакции
- [ ] `RowVersion` и понятная ошибка при конфликте правок
- [ ] Интеграционные тесты на настоящем Postgres через Testcontainers
- **Сломай нарочно:** сохрани части чека без транзакции и урони процесс посередине. Посмотри,
  что осталось в базе.

### Этап 2. Файлы и внешний мир
- [ ] Загрузка фото чека в MinIO, превью через imgproxy
- [ ] Курсы ЦБ с кэшем в Dragonfly на сутки
- [ ] Что отдаём, когда ЦБ недоступен: последний известный курс или ошибку — решить и обосновать
- **Сломай нарочно:** останови Dragonfly. Приложение должно продолжить работать, только медленнее.

### Этап 3. Наблюдаемость
- [ ] Логи в JSON → Vector → Loki
- [ ] Метрики: запросы, ошибки, длительность → Grafana-дашборд
- [ ] Ошибки в GlitchTip или Sentry
- **Сломай нарочно:** добавь медленный запрос и найди его по метрикам, не глядя в код.

### Этап 4. События и бюджеты
- [ ] Kafka в compose
- [ ] Outbox в `expenses`: событие пишется в таблицу в той же транзакции, что и трата,
  фоновая задача отправляет его в Kafka
- [ ] Сервис `budgets`: читает события, держит свою копию сумм, создаёт уведомления
- [ ] Идемпотентный консьюмер: повтор события не меняет сумму
- **Сломай нарочно:**
  - отправь событие в Kafka без outbox и урони сервис между записью в базу и отправкой;
  - отключи идемпотентность и прогони одно событие дважды;
  - останови `budgets`, добавь траты, запусти обратно — посмотри, как он догоняет.

### Этап 5. Импорт выписок
- [ ] Загрузка CSV в MinIO, событие «файл загружен»
- [ ] Разбор строк в фоне, событие на каждую найденную трату
- [ ] Защита от повторного импорта: ключ из полей банковской строки. Сравни два способа —
  ключ в Redis и уникальный индекс в Postgres
- [ ] Генератор выписки на миллион строк
- **Сломай нарочно:** `docker compose up --scale importer=3` — посмотри, как Kafka делит работу
  по партициям; убей один экземпляр посреди файла.

### Этап 6. Подписки
- [ ] Регулярные траты по расписанию в `Worker` сервиса `expenses`
- [ ] Ровно одно проведение: состояние «следующий запуск» в базе, блокировка между экземплярами
- **Сломай нарочно:** запусти два воркера и перезапусти один в момент проведения.

### Этап 7. Аналитика
- [ ] Генератор миллиона трат
- [ ] Отчёт по категориям за год в Postgres: `EXPLAIN`, индексы, замеры
- [ ] Debezium → Kafka → ClickHouse: таблица на Kafka engine, materialized view, ReplacingMergeTree.
  Схема — миграциями в `analytics/src/Migrator`, конфиг коннектора — в `infra/debezium`
- [ ] Сервис `analytics`: API того же отчёта поверх ClickHouse, сравнение времени с Postgres
- **Сломай нарочно:** переименуй колонку в Postgres и посмотри, что станет с потоком в ClickHouse.

### Этап 8. Фронт
- [ ] React + Apollo, codegen по своей схеме
- [ ] Две страницы: список трат с добавлением и бюджеты
- **Сломай нарочно:** поменяй поле в схеме бэка и посмотри, где это ловит codegen.
